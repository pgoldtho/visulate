# Technical Design Document: Core Schema & Entity Model

## 1. Context & Architectural Objectives

### 1.1 Overview
The legacy schema `pdb22.RNTMGR2` co-located operational rental management, county public records (`PR_*`), corporate records (`SUNBIZ_*`), and MLS feeds (`MLS_*`) in a monolithic Oracle 19c schema. This Technical Design Document specifies the extracted, standalone target schema for the **Property Management** bounded context on **PostgreSQL 16+ with PostGIS**.

### 1.2 Core Architectural Objectives
1. **Subsystem Isolation**: Completely eliminate foreign key dependencies on external subsystems (`PR_PROPERTIES`, `PR_LOCATIONS`, `MLS_LISTINGS`). External references are retained as optional integer identifiers (`prop_id`) for loose integration.
2. **PostgreSQL Idioms & Strict Types**:
   - Oracle unconstrained `NUMBER` mapped to specific integer or decimal types (`INTEGER`, `BIGINT`, `NUMERIC(12,2)`).
   - Oracle `DATE` (which stored time components) mapped explicitly to `DATE` (for pure calendar dates) or `TIMESTAMPTZ` (for point-in-time transactions).
   - Oracle sequences replaced with modern PostgreSQL standard `GENERATED BY DEFAULT AS IDENTITY`.
   - PostGIS `geometry(Point, 4326)` for spatial property and unit coordinates.
3. **Read Consistency & Auditability**:
   - Every operational entity includes `created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()` and `updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()`.
   - A deterministic row update trigger automatically maintains `updated_at` to support optimistic concurrency control in application services.
4. **Referential & Financial Integrity**:
   - Double-entry ledger structure with strict foreign keys between accounts, payments, journal entries, and allocations.
   - CHECK constraints on status enums, payment types, positive monetary amounts, and distinct debit/credit ledger accounts (`CONSTRAINT rnt_ledger_distinct_accounts CHECK (debit_account <> credit_account)`).

The target database uses the schema `property_management` (or standard public schema configured per tenant). The schema is structured into four core functional domains:

```

+--------------------------+----------------------------+-------------------------------+
|                                4. ACCOUNTING & LEDGER                                 |
|  - rnt_accounts (Chart of Accounts)                                                   |
|  - rnt_account_periods                                                                |
|  - rnt_payment_types & rnt_pt_rules                                                   |

```

## 3. Data Type Mapping Matrix

| Oracle 19c (`RNTMGR2`) | PostgreSQL 16+ Target Type | Design Rationale & Validation Rules |
| :--- | :--- | :--- |
| `NUMBER` (Primary Keys / IDs) | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 64-bit integer identity; supports existing legacy numeric keys during initial migration and auto-increments for new records. |
| `NUMBER` (Lookups / Small Codes) | `INTEGER` | Compact storage for lookup IDs, terms in months, year built. |
| `NUMBER(p, s)` (Amounts / Currency) | `NUMERIC(12, 2)` | Exact decimal representation for monetary calculations, rents, balances, fees, and payments. |
| `VARCHAR2(n)` | `VARCHAR(n)` | Retained exact length limits where enforced by domain rules (e.g. State `VARCHAR(2)`). |
| `VARCHAR2(4000)` / `CLOB` | `TEXT` | Variable length text with automatic PostgreSQL TOAST compression. |
| `BLOB` (Photos, Document Attachments) | `BYTEA` or URL Reference (`TEXT`) | Binary storage in database for backward compatibility; architecture provides transition to S3/Cloud storage URLs. |
| `DATE` (Transaction timestamps) | `TIMESTAMPTZ` | Standardized UTC timestamp with timezone. |
| `DATE` (Pure calendar dates) | `DATE` | For dates like `date_purchased`, `agreement_date`, `due_date`. |
| `SDO_GEOMETRY` (Points/Coordinates) | `geometry(Point, 4326)` | PostGIS standard WGS84 coordinates indexed via GiST. Extracted via `COALESCE(pr.GEO_LOCATION, pr.GEO_COORDINATES)`. |

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- Generic row update timestamp trigger function
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = clock_timestamp();
    RETURN NEW;
END;
```

## 5. View & Query Migration Specifications

The Oracle assessment identified 46 legacy outer join (`(+)`) queries across views and PL/SQL packages. These are rewritten to standard ANSI SQL:

### 5.1 Active Tenancy Agreement View (`v_active_tenancy_agreements`)
```sql
CREATE OR REPLACE VIEW v_active_tenancy_agreements AS
SELECT 
    ta.agreement_id,
    ta.unit_id,
    p.property_id,
    p.business_id,
    p.address1 || COALESCE(' Unit ' || pu.unit_name, '') AS full_address,
    p.city,
    p.state,
    p.zipcode,
    ta.start_date,
    ta.end_date,
    ta.amount AS monthly_rent,
    ta.deposit,
    ta.last_month,
    ta.status AS agreement_status,
    t.tenant_id,
    pe.first_name || ' ' || pe.last_name AS tenant_name,
    pe.phone1 AS tenant_phone,
    pe.email AS tenant_email
FROM rnt_tenancy_agreement ta
JOIN rnt_property_units pu ON ta.unit_id = pu.unit_id
JOIN rnt_properties p ON pu.property_id = p.property_id
LEFT JOIN rnt_tenant t ON ta.tenant_id = t.tenant_id
LEFT JOIN rnt_people pe ON t.people_id = pe.people_id
WHERE ta.status = 'ACTIVE';
```

### 5.2 Accounts Receivable Aging View (`v_ar_aging`)
```sql
CREATE OR REPLACE VIEW v_ar_aging AS
SELECT 
    ar.ar_id,
    ar.agreement_id,
    COALESCE(ar.business_id, p.business_id, t.business_id) AS business_id,
    p.name AS property_name,
    p.address1 AS property_address,
    pu.unit_name,
    pe.first_name || ' ' || pe.last_name AS tenant_name,
    ar.due_date,
    ar.amount AS total_amount,
    ar.amount_paid,
    (ar.amount - ar.amount_paid) AS balance_due,
    CURRENT_DATE - ar.due_date AS days_past_due,
    CASE 
        WHEN CURRENT_DATE <= ar.due_date THEN 'CURRENT'
        WHEN CURRENT_DATE - ar.due_date BETWEEN 1 AND 30 THEN '1-30 DAYS'
        WHEN CURRENT_DATE - ar.due_date BETWEEN 31 AND 60 THEN '31-60 DAYS'
        WHEN CURRENT_DATE - ar.due_date BETWEEN 61 AND 90 THEN '61-90 DAYS'
        ELSE '90+ DAYS'
    END AS aging_bucket
FROM rnt_accounts_receivable ar
LEFT JOIN rnt_tenancy_agreement ta ON ar.agreement_id = ta.agreement_id
LEFT JOIN rnt_property_units pu ON ta.unit_id = pu.unit_id
LEFT JOIN rnt_properties p ON pu.property_id = p.property_id
LEFT JOIN rnt_tenant t ON COALESCE(ar.tenant_id, ta.tenant_id) = t.tenant_id
LEFT JOIN rnt_people pe ON t.people_id = pe.people_id
WHERE ar.status IN ('OPEN', 'PARTIAL');
```
