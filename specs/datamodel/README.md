# specs/datamodel

This directory `specs/datamodel` serves as a central repository for various data models, database schema diagrams, and related documentation within the Visulate codebase. These assets are primarily in Microsoft Visio (`.vsd`) and Oracle XML Database Diagram (`.oxd_db`) formats, detailing database structures and relationships for specific functionalities (e.g., public records, rent management) and geographical regions (e.g., Brevard, Volusia counties in Florida). It also includes documentation for external data interactions, such as uploads to the Department of Revenue.

## Database Dependencies & Interactions

This directory primarily *defines* database structures rather than directly interacting with a live database. However, the files here represent the conceptual and logical models for several database components:

*   **Oracle Database Schema**: The `rntmgr.oxd_db` file explicitly describes parts of an Oracle database schema, including tables (e.g., `RNT_ACCOUNTS_PAYABLE`) and their foreign key constraints. This file serves as a blueprint for corresponding objects in an Oracle database instance.
*   **Visio Data Models**: The `.vsd` files (e.g., `brevard.vsd`, `public_records.vsd`, `volusia_datamodel.vsd`) contain visual representations of database schemas. These diagrams define tables, columns, relationships, and possibly other database objects, intended to be implemented in a relational database.
*   **External Data Sources**: The `dor_upload.doc` mentions `dor.myflorida.com/dor/property/resources/data.html`, implying that certain data models or data processing logic described here are designed to interact with or conform to standards set by the Florida Department of Revenue for property data.

## Maintenance & Modernization Notes

*   **Proprietary Formats**: The prevalence of `.vsd` (Microsoft Visio) files indicates a dependency on proprietary software for viewing and editing the data models. For improved accessibility, long-term archival, and version control integration, consider exporting these diagrams to more open formats such as SVG (already done for `rntmgr.svgz`), PNG, or ideally, generating standard SQL DDL scripts or an equivalent text-based ERD representation (e.g., using Mermaid or PlantUML).
*   **Oracle XML Database Diagram (`.oxd_db`)**: While XML is text-based and somewhat version-control friendly, this format is specific to Oracle JDeveloper. Ensure that the source JDeveloper project is also maintained or that DDL generation scripts are readily available and up-to-date.
*   **Thumbnail Cache (`Thumbs.db`)**: `Thumbs.db` files are automatically generated by Windows and should be added to `.gitignore` to prevent unnecessary clutter in the repository.
*   **Documentation Clarity**: The Word document (`dor_upload.doc`) might contain critical instructions. Consider converting important information from `.doc` to Markdown or a more universally accessible format.
*   **Schema Evolution**: Any changes to the underlying database schemas should be reflected and carefully versioned within these data model files. Maintaining a clear linkage between these diagrams and the actual implemented database schemas is crucial.
