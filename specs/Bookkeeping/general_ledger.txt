Visulate Requirements 
 – Double Entry Bookkeeping.
Peter Goldthorp, June 2009
Overview
The current version of Visulate uses single entry bookkeeping.  It maintains accounts payable and accounts receivable journals and tracks payments against them.  This limits its ability to support financial accounting.  It cannot support any activity that relies on account balances.  These include balance sheet creation, depreciation schedules, tracking owner’s capital, syndication agreements and  general business expenditure that does not relate to an individual property.  
Requirements
Enhance Visulate to support double entry bookkeeping.  
Functional Requirements
Chart of Accounts
Users should be able to record a chart of accounts for each business unit.  A chart of accounts is a list of accounts that a business uses to track assets, liabilities, income, expenses and capital.  Each account is classified with an account type which describes its characteristics.   
Visulate should maintain a default chart of accounts.  This will be used to create an initial chart of accounts for each business unit.  It will be copied to the business when a new business unit is created, once copied there is no connection between the default account and the business unit.  The user will be able to add or remove accounts from the business’s chart of accounts without affecting the default chart.
Payment Rules
The accounts payable and receivable screens are optimized to minimize data entry requirements.  The user presses an “Update List” button to generate a list of scheduled payments based on tenancy agreements and property expenses, pressing a “Paid” button for each scheduled entry records payment against it.  We need the ability to default the accounts that are debited and credited for each transaction.  This will limit the data entry requirements for new transactions and provide a mechanism to retrofit accounts onto existing ones.
Visulate classifies each transaction with a payment type (e.g. Rent, Repairs, Capital Improvements, etc).  These payment types should be used in conjunction with the transaction type to define payment rules for the business unit.  Every transaction is classified using one of the following types:
    • AP Scheduled – an accounts payable record has been created.
    • AP Paid – a payment has been entered for an accounts payable record.
    • AR Scheduled - an accounts receivable record has been created.
    • AR Paid – a payment has been received for an accounts receivable record.

We should also implement two usability enhancements based on user feedback:  
    1. The AR and AP screens should be divided into 2 sub-tabs for scheduled and unscheduled payments.
    2. Provide a way to see all unpaid and partially transactions on a single page.  Currently the user has to go back to previous months to record payments for tenants who are in arrears on their rent. 
In addition to this the AR and AP screens will need to accommodate closed accounting periods.  The requirements for this are described in a separate section of this document.
Journal Entries
Some transactions do not result in a payment.  For example the value of a property or an asset will depreciate over time.  These transactions need to be reflected in the books without creating a payment.  Visulate must provide the ability to record journal entries.  These entries should create rows in the general ledger and optionally allow a property to be assigned to them.
General Ledger
The General Ledger should be the main accounting record for a business unit.  It will maintain entries for each AP, AR and Journal transaction.  Every transaction should be posted to the ledger recording the accounts that were debited and credited.
A General Ledger summary screen should allow the user to review ledger entries for a given period.  It should provide a summary page that lists the sum of the debits and credit for the accounting period and a drill down screen where the user can review details of each transaction that touched the account.
The General Ledger screen should also allow the user to close the books for a business unit (see Accounting  Periods section below).
Reports
Two new reports should be created:
    1. Balance Sheet – should summarize the assets, liabilities and equity for a business unit on a given date.
    2. Income Statement – should provide a summary of the revenues, expenses and profit or loss for a business unit in a given period
Accounting Periods 
An accounting period will typically be a month, quarter or year.  At the end of an accounting period some accounts need to be zeroed out while others remain open.  Account balances for balance sheet accounts (assets, liabilities and equity) are carried over from one period to the next.  Income statement accounts (revenue, expenses and cost of goods sold) are reset to zero at the start of each period.
The user should be able to close the books at the end of an accounting period.  This process should calculate balances for each balance sheet account and record it in the database.  Once closed, users should not be able to edit the account entries for that period.  For example, a user should not be able to modify accounts payable or receivable entries for 2008 after the 2008 books have been closed.
An “undo close books” feature should also be available.  This should remove the most recent calculated balances from the database and re-open the accounting period for edits.
Use Cases
    • Create Business Unit
        1. User enters business unit details on the existing screen
        2. System reads the default chart of accounts and payment type rules and creates corresponding entries for the business unit.
        3. User reviews the chart of accounts and payment type rules and makes changes if necessary.
    • Track Accounts Payable and Receivable
        1. User presses the “Update List” button to generate payment rows.
        2. System populates the debit and credit accounts automatically based on “scheduled” payment rules for the business unit.
        3. User reviews the scheduled payment assignment and updates it if necessary.
        4. User presses the “Paid” button 
        5. System populates the debit and credit accounts automatically based on the “paid” payment rules for the business unit.
        6. User reviews the scheduled and paid assignments, updates if necessary then presses the “Save” button.
    • Close Books for Accounting Period
        1. User verifies all the AR and AP transactions have been recorded for the period.
        2. User creates Journal entries to reflect depreciation and other transactions.
        3. User reviews General Ledger entries to verify they are correct.
        4. User enters a period end date on the GL screen and presses the “Close Books” button.
        5. System calculates account balances for each balance sheet account.
        6. System locks entries to prevent insertion or modification of rows for the closed period.

New Concepts
Accounts and Account Types
Double entry bookkeeping accounts as described in the chart of accounts.  Each account is classified into one and only one account type.  The list of account types is fixed.  It includes assets, liabilities, equity, revenue, cost of goods sold and expenses.  Users can create new accounts using the chart of account screen.
Payment Types
A classification mechanism for payments, each payment is marked with an entry that describes it.  Examples include rent, capital improvements, depreciation and contra (a full list appears in the seed data requirements section).   The list of payment types is fixed.  Users cannot create new ones.
Transaction Types
Transaction types are classification mechanism for rows in the AR and AP journals.  Each row must be one of the following AR Scheduled, AR Paid, AP Scheduled AP Paid.
Payment Rules
Payment rules define account mappings for each unique combination of payment and transaction type.  They are used to seed the default debit and credit rows on the AR and AP screens.  The user may override these rules as required.
Data Model Changes
Double entry bookkeeping introduces eight new tables. No changes to existing tables are required.  A database view will be created to simplify general ledger reporting.

PL/SQL Requirements
    1. Generate insert, update, delete apis for each of the new tables.  Use gen_api2.sql for this (svn:visulate/code/generate).
    2. Create a new package RNT_GL_PKG to implement double entry bookkeeping business logic.  This should include procedures/functions for the following:
        a. Generate a default chart of accounts for a given business unit.  Copy values from rnt_default_account to rnt_accounts.
        b. Generate payment rules for a business unit.  Copy values from rnt_default_pt_rules to rnt_pt_rules.
        c. Get accounting period status for a given business unit and date.  Returns ‘CLOSED’ if the books have been closed and ‘OPEN’ if the period is editable.
        d. Get debit and credit account ids for a given transaction type and business unit.
        e. Generate contra entries for a date in the current accounting period in a given business unit.
        f. Close books and create new accounting period.  Accepts a business unit id, date and duration.  Sets the closed_yn flag in the current period to ‘Y’, creates a new period and calculates the balance amount for balance sheet accounts.
        g. Undo close books.  Deletes current account period and corresponding balances, sets closed_yn flag for previous period to ‘N’.
    3. Modify the transfer business unit functionality for a property.  Update the debit and credit account references for ledger entries that related to the property.

UI Changes
Four new screens and two new reports are required along with changes to the AR and AP screens.
Chart of Accounts
Used to create, update and delete rows in the RNT_ACCOUNTS table.  Drop down list allows user to select an account type.  This is populated using values in the RN_ACCOUNT_TYPES table.  Accounts should be displayed in Account Number order.  Current check box should be enabled for accounts of type Asset and Liability.  It is used to indicate assets and liabilities which have a life of less than a year.  The balance in these accounts will be displayed as current assets or liabilities on the Balance Sheet report for the business unit.
Screen should allow update access for Bookkeeping, Business Owner and Owner Manager roles.  All other roles should be Read Only.

Payment Rules
Reads the RNT_PT_RULES tables (with lookups to RNT_ACCOUNTS and RNT_PAYMENT_TYPES).  Allows the user to review and update payment rules for a business unit.  Screen should allow update access to Bookkeeping, Business Owner and Owner Manager roles.  All other roles should be read only.

Accounts Payable and Receivable
Make the following changes to the Accounts Payable and Receivable screens:
    1. Add a new “Unpaid” drop down value to the dropdown list at the top of the page.  Selecting this value should show all unpaid and partially paid items regardless of their due date.
    2. Break the screen into 2 sub-pages for scheduled and unscheduled payments.  The unscheduled payments are currently shown at the bottom of the main page.
    3. Prevent updates for transactions in a closed accounting period.  Display a “locked” icon and grey out fields for paid rows whose due dates occur in a closed period.  These rows should not be updateable.  Unpaid rows should not be greyed out.  The user should be able to record payment against them as long as the paid date is later than the end of the closed period.  A pre-update check should prevent the user from entering a date that falls inside a closed accounting period.
    4. Add a debit/credit column to the page.  These should allow the user to override the payment type rules for the AP Scheduled Debit account, AP Paid Credit account, AR Scheduled Credit account and AR Paid Debit account.  
        a. An AP scheduled transaction occurs when a row is created in the RNT_ACCOUNTS_PAYABLE table.  For example, the “update list” button is pressed on the AP  screen or the user creates a new “unscheduled” AP row.  An AP Paid transaction occurs when a row is created in RNT_PAYMENT_ALLOCATIONS table with a not null value for the AP_ID column.
        b. AR Scheduled transactions occur when rows are created in RNT_ACCOUNTS_RECEIVABLE.  AR Paid transactions occur when rows are created in RNT_PAYMENT_ALLOCATIONS with an AR_ID value.
    5. Reorder the other columns as shown in the examples below.  




Journal Entries
Create a new Journal entry screen to record details of transactions that are not recorded in AR or AP.  The screen should retrieve and display all rows in the RNT_LEDGER_ENTRIES table that join to RNT_PAYMENT_ALLOCATIONS where the (payment allocation) AR and AP ids are null.  It should insert  Date, Memo, Property, Debit and Credit information in the RNT_LEDGER_ENTRIES table and record the Amount in RNT_PAYMENT_ALLOCATIONS leaving the AR_ID and AP_ID columns null.
The Journal Entries screen should work in a similar way to the AR and AP screens with one exception.  The AR and AP screens show 2 ledger transactions for each row (scheduled and paid).  The Journal Entries screen shows one ledger transaction on each row.
An Update list button should calculate depreciation expenses for properties and equipment.  It should call a PL/SQL function that generates the rows.
