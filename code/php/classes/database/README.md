# PHP Database Classes (Data Access Layer)

This directory, `code/php/classes/database`, serves as the primary data access layer for the Visulate application. It contains a collection of PHP classes designed to encapsulate interactions with the Oracle database, specifically for both Public Records (`PR_`) and Rental Manager (`RNT_`) schemas. These classes provide structured methods for retrieving, inserting, updating, and deleting data related to various business entities such as properties, payments, accounts, users, leads, and more. They abstract the underlying SQL queries and PL/SQL package calls, offering a consistent interface for the application's business logic.

## Functional Overview

The classes within this directory manage the persistence and retrieval of application data. Each class typically corresponds to a specific domain entity or a functional area, providing methods to manipulate and query its associated data in the database. Key functionalities include:

*   **Property Management**: Handling details for public records properties and rental properties.
*   **Financial Management**: Managing accounts payable, accounts receivable, ledger entries, loans, and payments.
*   **User and Business Unit Management**: Controlling user access, roles, and organizational business units.
*   **Reporting and Analytics**: Generating various reports and summary analyses based on stored data.
*   **Data Integration**: Interfacing with external data sources like Sunbiz for corporate information and MLS listings.
*   **Configuration**: Managing application menus, lookup values, and error messages.

These classes are crucial for isolating the application logic from direct database calls, promoting maintainability and providing a layer for data validation and business rules enforcement at the data access level.

## Database Dependencies & Interactions

The classes in this directory heavily interact with a wide range of Oracle database objects, primarily tables and views, and frequently invoke PL/SQL packages for complex business logic and DML operations. The database schema primarily consists of two main prefixes:

*   **`PR_`**: Public Records related tables and views. These store data pertaining to properties, owners, taxes, sales, MLS listings, and corporate information.
*   **`RNT_`**: Rental Manager specific tables and views. These handle core application data like properties, business units, users, accounts, payments, agreements, leads, expenses, and more.

**General Interaction Patterns:**

*   **Data Retrieval**: Most classes directly query database views (e.g., `RNT_PROPERTIES_V`, `RNT_ACCOUNTS_RECEIVABLE_V`) or tables to fetch data. These views often denormalize data for easier reporting and display.
*   **Data Modification (Insert/Update/Delete)**: DML operations are almost exclusively handled by calling PL/SQL packages (e.g., `RNT_PROPERTIES_PKG.INSERT_ROW`, `RNT_ACCOUNTS_PAYABLE_PKG.UPDATE_ROW`). This centralizes business logic, ensures data integrity, and facilitates auditing.
*   **Lookup Values**: The `RNT_LOOKUP_VALUES_V` is frequently used across various classes (e.g., `rnt_agreement.class.php`, `rnt_properties.class.php`) to retrieve standardized lists for dropdowns and reference data.
*   **Ledger and Financial Transactions**: `RNT_LEDGER_ENTRIES`, `RNT_ACCOUNTS_PAYABLE`, `RNT_ACCOUNTS_RECEIVABLE`, and `RNT_PAYMENTS` are central to financial tracking, with classes like `rnt_journal.class.php` and `rnt_reports.class.php` performing complex aggregations and transactional processing involving these tables.
*   **User and Role Management**: `RNT_USERS`, `RNT_USER_ROLES`, and `RNT_BUSINESS_UNITS` are critical for authentication, authorization, and multi-tenancy.

**Examples of Specific Class-Database Interactions:**

*   `RNTProperties` class interacts with `RNT_PROPERTIES`, `RNT_PROPERTY_UNITS`, `RNT_LOANS`, `RNT_PROPERTY_VALUE`, `RNT_PROPERTY_PHOTOS`, and several related `_V` views for comprehensive property management.
*   `RNTAgreement` class relies on `RNT_TENANCY_AGREEMENT` and `RNT_AGREEMENT_ACTIONS` for managing tenant contracts and their lifecycle.
*   `RNTUser` uses `RNT_USERS`, `RNT_USER_ROLES`, and `RNT_BUSINESS_UNITS_V` to handle user authentication, password changes, and role assignments.

The extensive use of PL/SQL packages means that much of the transactional logic and data integrity rules reside within the Oracle database, with the PHP classes acting as an interface to trigger these operations.

## Maintenance & Modernization Notes

*   **Tight Coupling with PL/SQL**: The codebase exhibits strong coupling to Oracle PL/SQL packages. Any significant changes to the database schema or PL/SQL procedures would require corresponding updates in these PHP classes. Modernization might involve reducing reliance on specific package procedures for basic CRUD, potentially by moving more logic into the application layer or using an ORM.
*   **Database Abstraction**: The `rnt_base.class.php` provides a basic abstraction, but the direct use of OCI8-specific prepared statements and manual variable binding (`OCI8PreparedStatementVars.php`) indicates a low-level interaction model. Adopting a more robust database abstraction layer (DBAL) or a full-fledged ORM could simplify query construction, improve portability, and enhance security (e.g., by preventing SQL injection more robustly).
*   **Date Handling**: `UtlConvert.class.php` is used for converting date formats between display and database representations. This utility is critical and should be carefully managed if date handling logic is refactored.
*   **Error Handling**: The presence of `SQLExceptionMessage.class.php` suggests a custom approach to handling database errors. This might need to be integrated into a more comprehensive error logging and reporting framework if modernizing.
*   **Code Duplication**: While `RNTBase` offers common methods, there might still be opportunities to further consolidate repetitive SQL query patterns or DML logic across the many entity-specific classes.
*   **Performance**: Direct SQL queries and PL/SQL calls are often performant, but complex `SELECT` statements or numerous individual calls could benefit from analysis and optimization, potentially through caching or more efficient data retrieval strategies.
*   **Security**: Ensure all user inputs are properly sanitized and bound to prepared statements to prevent SQL injection vulnerabilities, especially given the manual binding approach.
