# Brevard Public Records Database Scripts

## Functional Overview
This directory contains SQL scripts designed for extracting, transforming, and loading (ETL) public records data specifically from Brevard County, Florida, into the Visulate database schema. The scripts handle various aspects of property data, including basic property details, ownership, usage, building characteristics, sales history, and tax information.

The typical workflow involves:
1.  **Setting up external connectivity**: Establishing an Oracle Heterogeneous Services link to a Microsoft Access Database (`.mdb`) file provided by Brevard County.
2.  **Staging Data**: Refreshing Oracle Materialized Views that pull data from the external source into local staging tables (`brd_tables`).
3.  **Processing Data**: Executing a sequence of PL/SQL scripts to populate the canonical `PR_PROPERTIES`, `PR_PROPERTY_OWNERS`, `PR_PROPERTY_USAGE`, `PR_BUILDINGS`, `PR_PROPERTY_SALES`, `PR_OWNERS`, `PR_DEED_CODES`, and `PR_TAXES` tables.
4.  **Maintaining Reporting Views**: Refreshing various `PR_` reporting Materialized Views after data updates.

This process ensures that Brevard County public records data is integrated into the Visulate system for analysis and display.

## Database Dependencies & Interactions

The scripts in this directory primarily interact with the following core Visulate Public Records (PR_) tables:

*   **`PR_PROPERTIES`**: The central table storing all property information. Most scripts either insert into or update this table.
*   **`PR_PROPERTY_OWNERS`**: Links properties to their current owners.
*   **`PR_PROPERTY_USAGE`**: Stores property use codes.
*   **`PR_BUILDINGS`**: Contains detailed building characteristics for properties.
*   **`PR_PROPERTY_SALES`**: Records sales transactions for properties.
*   **`PR_OWNERS`**: Stores details about property owners.
*   **`PR_DEED_CODES`**: Reference table for deed types.
*   **`PR_TAXES`**: Stores tax assessment and amount information for properties.

### Staging Tables
Data is initially loaded into several staging tables (e.g., `brd_properties`, `brd_buildings`, `brd_sales`, `brd_sales_properties`, `brd_usecodes`, `brd_beds`). These tables are typically created dynamically (`process.txt`) by querying Materialized Views that connect to the raw Brevard data source.

### PL/SQL Packages
The `PR_RECORDS_PKG` package is heavily utilized for standardized operations such as retrieving property IDs (`get_prop_id`), inserting new properties (`insert_property`), and managing property usage (`insert_property_usage`).

### External Data Source
The entire process relies on an external Brevard County data source, typically a Microsoft Access `.mdb` file, accessed via an Oracle Heterogeneous Services database link. The configuration for this link is detailed in `setup.txt`. Materialized Views (e.g., `pr_brevard_properties_mv`, `pr_brevard_taxes_mv`, etc.) are used to bridge this external data into the Oracle environment.

## Maintenance & Modernization Notes
*   **Heterogeneous Services Reliance**: The dependency on Oracle Heterogeneous Services connecting to an Access MDB via ODBC (`setup.txt`) represents an older integration pattern. Modernization efforts could explore more direct APIs (if available from Brevard County), flat-file ETL, or a more robust data warehousing approach to ingest and stage the data, potentially replacing the MDB as the primary source.
*   **Performance of `brevard7.sql`**: The script `brevard7.sql` is explicitly marked as running "very slowly." This indicates a potential bottleneck and suggests reviewing its SQL queries, indexing strategies, or data volume handling.
*   **ETL Process Orchestration**: The ETL process is currently described and executed through a series of `.txt` and `.sql` scripts (`process.txt`, `process2.txt`, `update_brevard.sql`). This could be streamlined and automated using a dedicated ETL tool (e.g., Apache NiFi, Airflow, or Oracle Data Integrator) for better monitoring, error handling, and scheduling.
*   **Hardcoded Mappings**: The use code mapping in `brevard2.sql` and millage rate lookup in `brevard7.sql` are hardcoded. Externalizing these mappings (e.g., into configuration tables or a dedicated lookup mechanism) would improve maintainability and flexibility for future changes.
*   **Data Quality**: The logic for identifying "current owner" in `brevard6.sql` relies on sales dates and `plat_page` from `PR_PROPERTY_SALES`. Any issues in the source sales data or its parsing could lead to inaccurate current ownership records. Regular data quality checks on `PR_PROPERTY_OWNERS` are recommended.
