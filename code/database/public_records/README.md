# Public Records Database Management

This directory, `code/database/public_records`, is a critical component of the Visulate application's data layer, specifically responsible for the comprehensive management of public records information. It orchestrates the Extraction, Transformation, and Loading (ETL) of property, owner, sales, and tax data from various Florida counties into the core `PR_PROPERTIES` and associated tables. Key functions include managing county-specific external source URLs, generating standardized alternative property keys for seamless external linking, and providing foundational scripts for schema maintenance and data updates.

## Database Dependencies & Interactions

This directory interacts primarily with two core public records tables: `PR_PROPERTIES` and `PR_SOURCES`.

*   **`PR_PROPERTIES` (Table)**:
    *   **Reads/Writes**: `afiedt.buf` and `generate_alt_keys.sql` directly query and update this table to generate and store `ALT_KEY` values, which are critical for external linking and data standardization.
    *   **Schema Modifications**: The `update_counties.txt` guide outlines steps to add `TOTAL_BEDROOMS` and `TOTAL_BATHROOMS` columns to this table, indicating its role in enriching property data.
    *   **Extensive Usage**: `PR_PROPERTIES` is a central table within the Visulate schema, also modified by various PL/SQL packages (`mls_mfr_pkg`, `pr_pums_pkg`, `pr_records_pkg`, `rnt_properties_pkg`) and numerous county-specific ETL scripts found within the subdirectories of `public_records`.

*   **`PR_SOURCES` (Table)**:
    *   **Writes**: `pr_source_urls.sql` updates the `PROPERTY_URL`, `TAX_URL`, and `PHOTO_URL` columns, providing the application with dynamic linking capabilities to official county data sources.
    *   **Schema Modifications**: `pr_source_length.sql` modifies the column lengths for the URL fields within this table to ensure they can accommodate required data.

## Submodules / Subdirectories

This directory organizes county-specific and related public records functionality into several subdirectories:

*   **`brevard`**: This directory contains SQL and PL/SQL scripts for the full ETL process of Brevard County public records data, from staging an external Access MDB via Oracle Heterogeneous Services to populating and maintaining various core public records tables in the Visulate database.
*   **`cities`**: This directory is responsible for generating, managing, and enriching city and county-level descriptive and metadata content within the Visulate public records database, utilizing both static definitions and dynamic generation techniques, often involving Oracle Spatial.
*   **`dor_notes`**: This directory contains SQL scripts for refreshing key materialized views within the Visulate public records database, specifically updating land, commercial, and county-level summary and sales data.
*   **`orange`**: This directory contains SQL scripts essential for importing and processing Orange County public records data into the Visulate database, covering properties, owners, sales, taxes, and usage, with a procedural setup guide for execution.
*   **`rent_estimates`**: This directory houses historical Fair Market Rent (FMR) data, ZIP-to-county mapping, and a requirements document that collectively define the data inputs and logical framework for generating property rent estimates within the Visulate application.
*   **`volusia`**: This directory contains SQL scripts and a documented process for extracting, transforming, and loading public records data from Volusia County into the Visulate database, populating core `PR_` tables with property, owner, sales, and tax information.

## Maintenance & Modernization Notes

*   **Procedural Update Guide**: The `update_counties.txt` file serves as a manual, step-by-step guide for county data updates. For enhanced robustness, consistency, and automation, these procedural steps could be integrated into a more formal build script, an Oracle job, or a dedicated ETL tool.
*   **Hardcoded `SOURCE_ID`s**: Scripts like `generate_alt_keys.sql` and `pr_source_urls.sql` rely on hardcoded `SOURCE_ID` values to identify different counties. As new counties are onboarded or existing ones change, these scripts require direct modification. A more flexible and scalable approach would involve a metadata-driven configuration, perhaps stored in a dedicated lookup table, to manage county-specific rules and URLs.
*   **`afiedt.buf` Usage**: The presence of `afiedt.buf` suggests ad-hoc SQL development. Any critical or recurring logic developed within such temporary files should ideally be formalized and moved into named, version-controlled SQL scripts or PL/SQL packages for better maintainability, clarity, and team collaboration.
*   **ETL Framework**: The overall ETL process across this directory and its subdirectories appears to be a collection of discrete SQL scripts and text-based instructions. Modernization efforts could focus on consolidating these into a more structured and resilient ETL framework, potentially utilizing Oracle Data Integrator, custom PL/SQL packages with robust logging and error handling, or an external scripting language (e.g., Python with `cx_Oracle`) for better orchestration and monitoring.
