# AWS Database Build Scripts

## Functional Overview
This directory contains SQL scripts and Oracle Data Pump parameter files essential for setting up and configuring an Oracle database instance, likely in an Amazon Web Services (AWS) environment. The scripts handle core database setup tasks such as creating necessary tablespaces, defining the primary application user (`rntmgr`), establishing network access control lists (ACLs) for external connectivity, and providing configurations for data import using Oracle Data Pump. These components collectively prepare a new database instance for the Visulate application's data and operations.

## Files & Component Responsibilities

| File Name          | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| :----------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `acl.sql`          | This script configures Oracle Network Access Control Lists (ACLs). It grants `execute` privileges on `UTL_HTTP`, `DBMS_CRYPTO`, and `SCHEDULER_ADMIN` to the `RNTMGR` user. More importantly, it creates and assigns `visulate1-acl.xml` to allow `RNTMGR` and `WEBACCESS` roles to establish outbound network connections to specific hosts, including MLS and Property Appraiser websites (`*.brevardmls.com`, `*.brevardpropertyappraiser.com`) and `*.offutt-innovia.com`, over all ports. This is critical for the application's external data retrieval functions.              |
| `create_ts2.sql`   | Defines and creates multiple Oracle BIGFILE tablespaces with `AUTOEXTEND ON` configured. These tablespaces are designed to segment and manage different types of application data, including `PR_PROPERTY_DATA`, `PR_CORP_DATA`, `MLS_DATA`, `RNT_DATA`, `MGT_DATA`, `SPATIAL_INDEX`, and `SPATIAL_WORK`. The sizes indicate the expected data volumes for each category.                                                                                                                                                                                                        |
| `create_user.sql`  | Creates the core `RNTMGR` database user, specifying its default and temporary tablespaces. It also grants `RNTMGR` unlimited quotas on all application-specific tablespaces (`rnt_data`, `mls_data`, `mgt_data`, `pr_property_data`, `pr_corp_data`, `spatial_index`, `spatial_work`). Additionally, it assigns various system privileges (`create session`, `create table`, `create procedure`, etc.) and object privileges (e.g., `execute` on `DBMS_CRYPTO` and `CTX_*` packages) required for the application's schema objects and functionality. The password is provided as a bind variable. |
| `import.par`       | An Oracle Data Pump parameter file used for performing a full data import. It specifies the `dpump_dir` directory for dump files, the `full_fri.dmp` dump file, and defines extensive schema and tablespace remapping rules. This file is crucial for importing a database backup from a different source environment into the `rntmgr` schema, correctly mapping source tablespaces (e.g., `users`, `pr_property_data2`) to the target tablespaces created by `create_ts2.sql`.                                                                                                          |
| `import_seq.par`   | A specialized Oracle Data Pump parameter file focusing on importing sequences. It uses `dpump_dir`, targets `seq_fri.dmp`, and remaps the `rntmgr_seq` schema to the `rntmgr` schema, ensuring that sequences from a source backup are correctly recreated and owned by the `rntmgr` user.                                                                                                                                                                                                                                                                                                    |
| `setup_datapump.sql`| This script creates an Oracle directory object named `dpump_dir`, mapping it to the `/u02/app/dpump` filesystem path. It then grants `READ` and `WRITE` permissions on this directory to the `rntmgr` user, which is a prerequisite for `RNTMGR` to use Oracle Data Pump for import/export operations, referencing the `.par` files in this directory.                                                                                                                                                                                                                                  |

## Database Dependencies & Interactions
This directory primarily defines and interacts with foundational Oracle database objects and features:
*   **Users**: Creates and configures the `RNTMGR` user.
*   **Roles**: Creates the `WEBACCESS` role and grants `SCHEDULER_ADMIN` to `RNTMGR`.
*   **Tablespaces**: Creates several BIGFILE tablespaces (`PR_PROPERTY_DATA`, `PR_CORP_DATA`, `MLS_DATA`, `RNT_DATA`, `MGT_DATA`, `SPATIAL_INDEX`, `SPATIAL_WORK`).
*   **Privileges**: Grants numerous system privileges (e.g., `CREATE SESSION`, `CREATE TABLE`, `CREATE PROCEDURE`) and object privileges (e.g., `EXECUTE` on `UTL_HTTP`, `DBMS_CRYPTO`, `CTX_*` packages) to the `RNTMGR` user.
*   **DBMS_NETWORK_ACL_ADMIN**: Utilizes this PL/SQL package to create and manage network ACLs, enabling secure outbound network access for the database.
*   **Oracle Data Pump**: Configures the environment for Data Pump operations by creating a directory object and defining import parameter files (`.par`).
*   **Oracle Text (CTX_*)**: Grants privileges on Oracle Text packages, indicating the application likely uses full-text indexing and search capabilities.

## Maintenance & Modernization Notes
*   **Password Management**: The `create_user.sql` script uses a bind variable `&1` for the password. Ensure secure handling of this password during deployment (e.g., using secure parameter stores or environment variables rather than hardcoding).
*   **Tablespace Sizing**: The initial sizes for tablespaces in `create_ts2.sql` are fixed. While `AUTOEXTEND` is enabled, monitor growth to ensure underlying storage capacity and performance remain adequate. Consider using Oracle Automatic Storage Management (ASM) or flexible AWS storage options for better scalability.
*   **Network ACLs**: The `acl.sql` script grants broad access (`1-9999` ports) to specific hosts. Regularly review and restrict port ranges to the minimum necessary for enhanced security. The hosts listed (`*.brevardmls.com`, etc.) indicate a dependency on external APIs; monitor these for changes in URLs or security requirements.
*   **Data Pump Compatibility**: Ensure that the Data Pump dump files (`.dmp`) are compatible with the target Oracle database version. Parameter files may need adjustments for major version upgrades.
*   **Permissions Audit**: Periodically audit the grants in `create_user.sql` and `acl.sql` to ensure the principle of least privilege is maintained and unnecessary permissions are revoked, especially for `SCHEDULER_ADMIN` and `CTX_*` packages.
*   **Script Idempotency**: These scripts are primarily designed for initial setup. While some commands (like `CREATE USER IF NOT EXISTS`) are not natively supported, subsequent runs would typically fail on existing objects. Consider adding checks or using `CREATE OR REPLACE` where appropriate for better idempotency if these scripts are to be run multiple times in a lifecycle.
